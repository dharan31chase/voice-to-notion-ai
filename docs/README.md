### When You Modify Code
1. Update [project-state.md](project-state.md) if you make a major decision
2. Update [refactoring-plan.md](refactoring-plan.md) if you complete a phase/step
3. Update relevant technical docs if you change architecture
4. Always update "Last Updated" dates

### When You Complete a Milestone
1. Create a milestone completion doc (like milestone-1.1-completion.md)
2. Update [project-state.md](project-state.md) with decision
3. Update [refactoring-plan.md](refactoring-plan.md) progress
4. Update this index if you add new docs

### When You Have Product Insights (NEW)
1. Create a walkthrough doc in `walkthroughs/YYYY-MM-DD-[topic].md`
2. Extract key learnings into `insights/` when patterns emerge
3. Reference related PRDs, tech requirements, and session logs
4. Update this index to include new content

### When Philosophy Evolves (NEW)
1. Update [context/philosophy-and-strategy.md](context/philosophy-and-strategy.md) with new insights
2. Increment version number and update version history
3. Consider updating [context/one-pager-vision.md](context/one-pager-vision.md) if core vision shifts
4. Reference voice logs or session logs that triggered the update

## 📖 What Makes a Good Walkthrough?

Walkthroughs capture **how the system actually works** in practice, not just how it's designed to work. Good walkthroughs include:

- **Real metrics**: Actual iteration rates, time savings, success rates
- **Usage patterns**: How you actually interact with the system
- **Open questions**: What you're still figuring out
- **System evolution**: How behavior changes over time
- **Design insights**: What you learned that informs future work

See [walkthroughs/2025-11-11-context-sync-quality-metrics.md](walkthroughs/2025-11-11-context-sync-quality-metrics.md) for an example.
